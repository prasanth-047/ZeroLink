# ZeroLink Project Review

**Reviewed:** 2026-11-20
**Scope:** Repository inventory, architecture and execution-plan docs, manifests, protocol/core code, Windows/Android transport paths, Sefirah product references, and verification scripts. Includes the current pairing audit status, post-format build checks, and idle working-set measurements.

## Project at a glance

ZeroLink is a cross-device Android-to-Windows companion app. The intended feature set includes clipboard sync, phone notifications and replies, media controls, photo/file access, telemetry, and Android screen mirroring with remote input. The workspace has three Rust crates (`zerolink-core`, `zerolink-win`, and Android JNI bindings) and a Kotlin Android app.

## Repository map

- `zerolink-core/`: shared packet types, binary framing, cryptography, errors, and dual-radio state machine.
- `zerolink-win/`: Rust Windows client, with BLE/TCP transport, clipboard, notifications, media, cloud-filter file handling, UI, and screen-viewer modules.
- `zerolink-android/app/`: Kotlin services and UI for L2CAP/network transport, clipboard, notifications, media, Wi-Fi, and H.265 screen capture.
- `zerolink-android/zerolink-jni/`: native bridge to the shared Rust core.
- `schemas/zerolink.fbs`: FlatBuffers schema; `scripts/`: a Windows verification script and Android peer simulator.
- `ARCHITECTURE.md`: protocol/design blueprint; `zerolink-execution-plan.md`: claimed implementation and remaining-work status.

## Current picture

The core defines 20-byte framed packets and payload types for handshake, clipboard, notifications/actions, media, screen input, Wi-Fi wake, and file metadata/chunks. The Android debug app assembles, and the Windows screen viewer prefers asynchronous D3D11-aware Media Foundation hardware decoding with direct D3D11 presentation and CPU/GDI plus synchronous software fallbacks. The Windows Cloud Files callback honors the optional contiguous range hint and preserves a positive range length on failed transfers. A pairing-free integration probe and the encrypted mock-peer verifier both hydrated and byte-verified a 4 MiB placeholder through `FETCH_DATA` and `CfExecute`; five range/error-path tests pass. The encrypted peer run also confirmed mutual key verification and temporary DPAPI secret persistence, then removed the secret during cleanup. The Android app requests image access only when the user starts photo catalog sync, with Android 14 selected-photo handling. Its latest API 36 instrumentation run passed 10 tests, including notification reply dispatch, encrypted media-range serving, and plain-text-only remote clipboard decoding. TCP pairing and PSK reconnect are verified on an API 36 emulator. Physical BLE and interactive reply/media/screen-mirror checks remain open.

There are material gaps between those claims and the source reviewed:

1. **Pairing and PSK reconnect are verified over TCP on an API 36 emulator.** The six-digit codes matched, both local approvals were accepted, mutual key confirmation succeeded, and encrypted heartbeat/media-state packets flowed. After restarting the Windows daemon against the protected stores, the PSK proof succeeded without another prompt. A later reconnect also stayed healthy while Windows rejected a second simultaneous TCP socket. Physical BLE pairing remains open. This is trust-on-first-use via a shared PSK, not a manufacturer identity.
2. **The isolated Windows pairing audit passed.** The verifier completed mutual key confirmation, sent encrypted first-pair approval, and observed a 320-byte protected `paired-peer.dat` before cleanup. Both the earlier pairing-only run and the latest hydration run recorded only secret presence and byte length; cleanup removed the secret. The API 36 daemon restart/reconnect separately demonstrated saved-PSK reload. Android proof validation, timeout rejection, the production dialog's Reject action, Keystore save/reload/clear, and lost-wrapping-key recovery pass emulator instrumentation; cross-device forget and physical BLE remain open.
3. **Synthetic feature traffic reached Windows in the earlier run.** A synthetic notification was received; the simulator clipboard value was injected into the Windows clipboard; heartbeat/media state was received; and the catalog contained three entries. Windows Cloud Filter access was available in that test profile, but the run confirmed catalog reception rather than placeholder hydration. Clipboard injection is now opt-in for routine simulator runs. Earlier test logs remain under `.codex-target\simulator-profile\logs`.
4. **Screen-mirroring startup works, but frame delivery remains unverified.** The Android API 36 consent flow and MediaProjection foreground-service promotion now succeed. Encoder discovery prefers HEVC surface input, falls back to flexible YUV, and runs on a worker thread. The emulator exposes no supported HEVC size/rate configuration for the requested `1080x2209` capture or the lower sizes checked, so the encoder stops before emitting a frame. Windows prefers a D3D11-aware asynchronous Media Foundation hardware MFT and presents supported NV12 output surfaces directly through a D3D11 video processor and swap chain. CPU readback/GDI and a synchronous software MFT remain fallbacks. Android 14+ resizes and restarts the encoder on MediaProjection resize callbacks; Android 10–13 use a display-listener fallback.
5. **Further runtime and performance evidence remains open.** Notification reply/dismiss, real Android notifications, media commands, screen mirroring, physical BLE, and physical-device behavior are untested. Three isolated no-peer idle snapshots after the delayed working-set trim measured 14.25–14.26 MB working set and 3.11–3.35 MB private memory, meeting the `<15 MB` idle target. A forced API 36 deep-idle snapshot reported `mWakeLockSummary=0x0` and `Wake Locks: size=0`; physical-device Doze and battery impact remain open, as does connected-session memory.

These are review findings, not a full security audit. Payload implementations and OS integrations still need targeted inspection before relying on every feature.
